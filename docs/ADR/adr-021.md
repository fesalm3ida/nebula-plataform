# ADR-021 — Playlist Domain and Device Assignment

- **Status:** Accepted
- **Data:** 2026-07-27
- **Versão:** Nebula Core v0.3.x
- **Autores:** Nebula Team

---

# Contexto

O Nebula Core é responsável por fornecer aos dispositivos autorizados a
configuração necessária para acesso ao conteúdo disponibilizado pela plataforma.

Até este momento, o Core já implementa:

- autenticação de Devices;
- autorização baseada em JWT;
- ciclo de vida de Sessions;
- persistência;
- separação em Clean Architecture.

O próximo passo consiste em modelar o domínio responsável pelo gerenciamento
das Playlists utilizadas pelos dispositivos.

O objetivo desta ADR é definir como uma Playlist será representada dentro do
domínio do Nebula, como será vinculada aos Devices e como será disponibilizada
ao Nebula Player.

---

# Problema

O Nebula deverá suportar diferentes formatos de fornecimento de conteúdo
(M3U, Xtream Codes, Stalker, entre outros), porém sem acoplar o restante do
domínio às particularidades de cada tecnologia.

Além disso, a plataforma necessita permitir que administradores realizem o
cadastro manual das fontes de conteúdo através do Nebula Admin.

---

# Decisão

Uma Playlist será tratada como uma abstração de uma fonte de conteúdo.

Ela representa uma configuração de acesso, independentemente do protocolo
utilizado para obtenção do conteúdo.

O Nebula Core não considera uma Playlist como um arquivo M3U, uma conta
Xtream ou uma configuração Stalker.

Todos esses formatos passam a ser apenas implementações possíveis de uma
mesma abstração.

---

# Modelo Conceitual

```
Playlist
├── id
├── name
├── format
├── source_url
├── status
├── created_at
└── updated_at
```

---

# Formatos

O domínio deverá permitir a evolução para múltiplos formatos.

Inicialmente serão previstos:

- M3U
- Xtream Codes
- Stalker

Entretanto, apenas o formato **M3U** será implementado durante a primeira
versão do módulo.

Os demais formatos permanecem previstos para futuras implementações sem exigir
alterações estruturais no domínio.

---

# Cadastro

As Playlists serão cadastradas manualmente através do Nebula Admin.

O administrador informará:

- nome;
- formato;
- URL da Playlist;
- status.

Não existirá sincronização automática com provedores externos nesta etapa do
projeto.

---

# Associação

Um Device não possuirá uma Playlist diretamente.

O relacionamento será realizado através de uma entidade intermediária.

```
Device
    │
    ▼
PlaylistAssignment
    │
    ▼
Playlist
```

Essa abordagem desacopla o Device da origem do conteúdo e permite futuras
evoluções, como:

- múltiplos perfis;
- múltiplas Playlists;
- associação por cliente;
- políticas administrativas.

---

# Provisionamento

O Nebula Player nunca consultará diretamente o Nebula Admin.

Todo provisionamento ocorrerá exclusivamente através do Nebula Core.

Fluxo previsto:

```
Nebula Player
      │
      ▼
Autenticação
      │
      ▼
GET /me/provisioning
      │
      ▼
Nebula Core
      │
      ▼
PlaylistAssignment
      │
      ▼
Playlist
      │
      ▼
Resposta ao Player
```

O Core será responsável por localizar a Playlist ativa associada ao Device
autenticado.

---

# Atualizações

As alterações realizadas em uma Playlist serão persistidas diretamente.

Não será adotado versionamento de Playlists.

A atualização ocorrerá simplesmente através da modificação da entidade
persistida.

Os dispositivos passarão a utilizar a configuração atualizada durante o
próximo processo de provisionamento.

---

# Monitoramento

Esta ADR não define mecanismos de monitoramento.

Entretanto, a modelagem proposta permite futuras funcionalidades como:

- verificação de disponibilidade da URL;
- validação da estrutura da Playlist;
- detecção de falhas de acesso;
- monitoramento de conteúdos específicos;
- telemetria integrada ao Nebula Monitor.

Essas funcionalidades serão tratadas em ADRs futuras.

---

# Consequências

## Benefícios

- abstração independente do formato;
- baixo acoplamento;
- domínio simples;
- fácil evolução para novos provedores;
- integração transparente com o Nebula Player;
- compatível com Clean Architecture.

## Trade-offs

- sincronização automática não faz parte do escopo atual;
- catálogo de conteúdos não será persistido nesta etapa;
- apenas M3U possuirá implementação inicial.

---

# Alternativas Consideradas

## Associação direta Playlist → Device

Rejeitada.

Acoplaria o Device diretamente à origem do conteúdo e dificultaria futuras
evoluções do domínio.

---

## Versionamento de Playlists

Rejeitado.

Embora facilite rollback e auditoria, adicionaria uma complexidade
desnecessária para o estágio atual do projeto.

O MVP não demanda múltiplas versões simultâneas de uma Playlist.

---

## Sincronização automática de provedores

Rejeitada para o MVP.

A sincronização automática será considerada futuramente quando o Nebula
Monitor e os mecanismos de observabilidade forem implementados.
