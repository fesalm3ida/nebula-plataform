# ADR-018 — Persistence Model Isolation

- **Status:** Accepted
- **Data:** 2026-07-12
- **Autores:** Nebula Software House
- **Decisores:** Arquitetura Nebula
- **Relacionados:**
  - ADR-001 — Stateless Player
  - ADR-014 — Session Lifecycle
  - ADR-015 — Session Heartbeat
  - ADR-016 — Session Presence Tracking
  - ADR-017 — PostgreSQL as Primary Persistence
- **Impacto:** Backend / Persistence / Domain

---

# Contexto

Até esta etapa, toda a persistência do Nebula Core é realizada por meio de repositórios em memória (`InMemoryRepository`).

Com a introdução do PostgreSQL, SQLAlchemy e Alembic, surge uma decisão arquitetural importante:

> O domínio deve ou não conhecer a tecnologia de persistência?

Acoplar entidades de domínio diretamente ao ORM simplifica implementações iniciais, porém reduz a independência da camada de domínio e aumenta o custo de manutenção e evolução da arquitetura.

Como o Nebula adota princípios de Domain-Driven Design (DDD) e Clean Architecture, torna-se necessário estabelecer uma separação clara entre:

- Modelo de Domínio
- Modelo de Persistência

---

# Problema

Permitir que entidades do domínio herdem classes do SQLAlchemy ou utilizem anotações específicas do ORM cria dependência direta da infraestrutura.

Exemplos de acoplamento indesejado:

- `DeclarativeBase`
- `Mapped`
- `mapped_column`
- `relationship`
- `ForeignKey`
- sessões SQLAlchemy
- detalhes de persistência

Isso faria com que regras de negócio dependessem da tecnologia de banco de dados.

---

# Decisão

O Nebula adota isolamento completo entre Domínio e Persistência.

As entidades do domínio continuarão sendo objetos Python puros (Plain Python Objects).

Todo código relacionado ao SQLAlchemy ficará restrito à camada de infraestrutura.

A comunicação entre ambos ocorrerá exclusivamente através de Mappers.

---

# Arquitetura

```
                 ┌──────────────────────┐
                 │      FastAPI         │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │     Use Cases        │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │ Repository Interface │
                 └──────────┬───────────┘
                            │
             ┌──────────────┴──────────────┐
             ▼                             ▼
 InMemoryRepository             SQLAlchemyRepository
                                            │
                                            ▼
                                   SQLAlchemy Models
                                            │
                                            ▼
                                      PostgreSQL
```

O Domínio permanece completamente isolado da camada ORM.

---

# Separação de responsabilidades

## Domínio

Responsável por:

- regras de negócio;
- invariantes;
- entidades;
- value objects;
- enums.

Não conhece:

- SQLAlchemy;
- PostgreSQL;
- Alembic;
- sessões;
- consultas SQL.

---

## Infraestrutura

Responsável por:

- models ORM;
- consultas SQL;
- persistência;
- migrations;
- sessões do banco;
- transações.

Não contém regras de negócio.

---

## Mappers

Os mappers são responsáveis pela conversão bidirecional entre:

```
Device
        ⇄
DeviceModel
```

e

```
Session
        ⇄
SessionModel
```

Nenhuma outra camada poderá realizar essa conversão diretamente.

---

# Estrutura adotada

```
app/
└── infrastructure/
    └── persistence/
        ├── database.py
        ├── base.py
        ├── models/
        │   ├── device_model.py
        │   └── session_model.py
        │
        ├── mappers/
        │   ├── device_mapper.py
        │   └── session_mapper.py
        │
        └── repositories/
            ├── sqlalchemy_device_repository.py
            └── sqlalchemy_session_repository.py
```

---

# Benefícios

Esta decisão proporciona:

- isolamento do domínio;
- independência tecnológica;
- facilidade para testes unitários;
- substituição futura do mecanismo de persistência;
- menor acoplamento;
- maior legibilidade;
- manutenção simplificada.

---

# Consequências

## Positivas

- Domínio permanece puro.
- Testes unitários não dependem do banco.
- SQLAlchemy fica encapsulado.
- Regras de negócio permanecem independentes.
- Evolução futura facilitada.

## Negativas

- Necessidade de escrever Mappers.
- Maior número de classes.
- Conversões adicionais entre domínio e infraestrutura.

O custo adicional é considerado pequeno diante dos benefícios arquiteturais.

---

# Princípios derivados

A partir desta ADR ficam estabelecidas as seguintes regras:

1. Entidades de domínio nunca herdam classes do SQLAlchemy.

2. Nenhuma entidade do domínio utilizará `Mapped`, `mapped_column`, `relationship` ou qualquer recurso específico do ORM.

3. Todo acesso ao banco ocorrerá através de Repository Interfaces.

4. Apenas a camada de infraestrutura conhece SQLAlchemy.

5. Apenas os Mappers convertem objetos de domínio para modelos ORM e vice-versa.

6. Casos de uso nunca manipulam objetos ORM diretamente.

7. O domínio deve continuar executando integralmente sem a existência de um banco de dados.

---

# Status

**Aceita.**

Esta ADR passa a reger toda implementação de persistência do Nebula Core utilizando PostgreSQL, SQLAlchemy e Alembic.
