# ADR-020 — Bearer Authentication e Identidade do Device

- **Status:** Implementada
- **Data:** 2026-07-16
- **Autor:** Nebula Software House
- **Decisores:** Equipe Nebula
- **Versão:** First Light
- **Relacionadas:** ADR-017, ADR-018, ADR-019
- **Impacto:** Core / Segurança / API / Player

---

## Contexto

O Nebula Core já autentica Devices por meio do endpoint:

```http
POST /auth/device
```

Após validar:

- `device_id`;
- `device_key`;
- `fingerprint`;
- status ativo do Device;

o Core emite um JWT assinado contendo a identidade do Device autenticado.

Entretanto, os demais endpoints ainda não utilizam esse token para identificar e autorizar o Device que realiza a requisição.

A evolução da plataforma exige que operações protegidas recebam o token no header HTTP:

```http
Authorization: Bearer <access_token>
```

O token deverá ser validado e convertido em uma identidade de domínio antes que a requisição alcance a lógica principal do endpoint.

---

## Problema

Como proteger endpoints do Nebula Core utilizando JWT sem:

- duplicar lógica de autenticação nas rotas;
- expor detalhes do PyJWT à camada de API;
- permitir que Devices bloqueados, revogados ou expirados continuem operando;
- acoplar regras de domínio ao protocolo HTTP?

---

## Decisão

O Nebula Core utilizará autenticação HTTP Bearer para endpoints protegidos.

Será criada uma dependência FastAPI responsável por:

1. extrair o token Bearer;
2. validar o JWT por meio de `AccessTokenService`;
3. obter o `device_id`;
4. carregar o Device pelo `DeviceRepository`;
5. verificar o status atual do Device;
6. retornar a entidade `Device` autenticada para a rota.

A dependência principal será:

```python
get_current_device()
```

As rotas protegidas receberão diretamente:

```python
current_device: Device = Depends(get_current_device)
```

---

## Fluxo

```text
HTTP Request
      │
      │ Authorization: Bearer <jwt>
      ▼
HTTPBearer
      │
      ▼
get_current_device()
      │
      ├── valida token
      ├── obtém device_id
      ├── busca Device
      └── valida status
      │
      ▼
Device autenticado
      │
      ▼
Protected Route
```

---

## Header de Autenticação

O formato aceito será:

```http
Authorization: Bearer <token>
```

Exemplos rejeitados:

```http
Authorization: Basic abc123
```

```http
Authorization: Token abc123
```

```http
Authorization: Bearer
```

```http
Authorization: Bearer <token-inválido>
```

---

## Identidade Autenticada

A identidade autenticada será representada pela própria entidade de domínio:

```python
Device
```

A rota não receberá apenas um UUID.

Isso permite acesso seguro a informações como:

- `device_id`;
- `status`;
- `platform`;
- `app_version`;
- `fingerprint`.

Exemplo:

```python
def heartbeat(
    current_device: Device = Depends(get_current_device),
) -> Response:
    ...
```

---

## Verificação do Device

Mesmo que o JWT seja válido, o Device deverá ser consultado no banco.

Isso permite rejeitar imediatamente Devices que, após a emissão do token, tenham sido:

- bloqueados;
- revogados;
- expirados;
- removidos;
- desativados.

O JWT prova que o token foi emitido pelo Core.

O banco prova que o Device continua autorizado neste momento.

---

## Status Permitido

Somente Devices com status:

```text
active
```

poderão acessar endpoints protegidos.

No código, isso corresponde a `DeviceStatus.ACTIVE`.

Os demais status serão rejeitados:

```text
pending
blocked
revoked
expired
```

---

## Respostas HTTP

### Token ausente

```http
401 Unauthorized
```

### Esquema de autenticação inválido

```http
401 Unauthorized
```

### Token inválido

```http
401 Unauthorized
```

### Token expirado

```http
401 Unauthorized
```

### Device inexistente

```http
401 Unauthorized
```

A inexistência do Device não será diferenciada de um token inválido para evitar exposição desnecessária de informações.

### Device não ativo

```http
403 Forbidden
```

### Header de resposta

Respostas `401` deverão incluir:

```http
WWW-Authenticate: Bearer
```

## Separação de Responsabilidades

### `app/api/security/bearer.py`

Responsável por:

- definir o esquema `HTTPBearer` utilizado pelo FastAPI;
- expor `bearer_scheme`;
- extrair e descrever o esquema Bearer no OpenAPI;
- entregar as credenciais à dependência de identidade autenticada.

Este módulo não deverá validar JWT, carregar Devices ou aplicar regras de autorização.

### `AccessTokenService`

Responsável por:

- validar assinatura;
- validar algoritmo;
- validar emissor;
- validar audiência;
- validar expiração;
- validar claims;
- retornar o `device_id`.

A aplicação continua dependendo apenas desse contrato.

A implementação concreta JWTAccessTokenService permanece na infraestrutura.

### `DeviceRepository`

Responsável por:

- carregar o Device persistido.

### `app/api/security/services.py`

Responsável por:

- fornecer implementações concretas de serviços de segurança;
- conter `get_access_token_service()`;
- centralizar futuramente providers relacionados a autenticação e autorização.

### `app/api/security/current_device.py`

Responsável por:

- implementar `get_current_device()`;
- validar o token por meio de `AccessTokenService`;
- obter o `device_id`;
- carregar o Device pelo `DeviceRepository`;
- validar se o Device existe;
- validar se o status atual do Device é `active`;
- retornar a entidade `Device` autenticada.

Falhas de autenticação deverão retornar `401` com:

```http
WWW-Authenticate: Bearer
```

Devices existentes, porém não ativos, deverão retornar `403`.

### `app/api/security/permissions.py`

Responsável por reservar espaço para autorização futura, incluindo:

- ownership de recursos;
- escopos;
- permissões administrativas.

Poderá permanecer sem implementação nesta fase.

### `app/api/security/exceptions.py`

Responsável por centralizar exceções específicas da camada HTTP de segurança.

Conceitos previstos:

- `AuthenticationRequiredError`;
- `InvalidAccessTokenError`;
- `AuthorizationDeniedError`.

Essas exceções não devem duplicar exceções de domínio ou de aplicação sem necessidade.

### `app/api/security/__init__.py`

Responsável por exportar apenas os componentes públicos necessários da camada de segurança.

### Rota

Responsável apenas pela operação de negócio.

A rota não deverá:

- decodificar JWT;
- acessar claims diretamente;
- verificar assinatura;
- consultar headers manualmente;
- duplicar validações de status.

## Endpoints Protegidos

A proteção será aplicada gradualmente.

Primeiros candidatos:

```http
POST /sessions
POST /sessions/{session_id}/heartbeat
POST /sessions/{session_id}/end
```

O endpoint:

```http
POST /auth/device
```

permanecerá público, pois é o ponto de emissão do token.

O registro de Device também permanecerá público durante o fluxo inicial:

```http
POST /devices/register
```

A ativação de Device não será protegida por autenticação de Device. Ela será futuramente movida para uma API administrativa autenticada.

---

## Regra de Propriedade da Session

Após a autenticação Bearer, operações de Session deverão validar também se:

```text
session.device_id == current_device.device_id
```

Um Device não poderá:

- enviar Heartbeat para Session de outro Device;
- encerrar Session de outro Device;
- consultar ou manipular recursos pertencentes a outro Device.

Essa validação de propriedade será implementada nos casos de uso ou em serviços de aplicação, não apenas na rota.

---

## OpenAPI

O FastAPI deverá expor no Swagger o esquema:

```text
HTTPBearer
```

Endpoints protegidos deverão exibir o botão:

```text
Authorize
```

O token será informado sem o prefixo manual quando o Swagger administrar o esquema Bearer.

---

## Segurança

A aplicação deverá:

- fixar o algoritmo permitido no servidor;
- nunca confiar no algoritmo informado pelo token;
- rejeitar tokens sem claims obrigatórias;
- não registrar tokens completos em logs;
- não retornar detalhes internos de falha criptográfica;
- não expor se um determinado Device existe;
- manter a chave JWT fora do repositório;
- consultar o status atual do Device no banco.

---

## Logs

Logs de autenticação poderão registrar:

- tipo de falha;
- horário;
- endpoint;
- `device_id`, apenas quando extraído com segurança;
- endereço ou contexto da requisição, quando disponível.

Não deverão registrar:

- access token completo;
- chave JWT;
- device key;
- fingerprint completo;
- credenciais sensíveis.

## Benefícios

- autenticação centralizada;
- separação explícita entre autenticação, autorização e infraestrutura de segurança;
- rotas mais simples;
- identidade de domínio disponível diretamente;
- rejeição imediata de Devices bloqueados;
- redução de duplicação;
- suporte nativo ao Swagger;
- base pronta para autorização;
- organização dedicada em `app/api/security/`;
- compatibilidade com o Nebula Player.

---

## Trade-offs

- uma consulta ao banco por requisição protegida;
- dependência adicional no ciclo da requisição;
- necessidade de testes de integração;
- necessidade futura de cache ou otimização;
- aumento da complexidade da camada de segurança.

A consulta ao banco é aceita nesta fase para garantir que alterações de status tenham efeito imediato.

---

## Alternativas Consideradas

### Confiar somente no JWT

Rejeitada.

Um Device bloqueado continuaria autenticado até a expiração do token.

### Decodificar JWT em cada rota

Rejeitada.

Criaria duplicação, inconsistência e maior superfície para erros de segurança.

### Middleware global

Adiado.

Nem todos os endpoints exigem autenticação, e a injeção por dependência permite aplicar segurança de forma explícita e granular.

### Retornar apenas `device_id`

Rejeitada como padrão principal.

A entidade completa reduz consultas duplicadas e entrega às rotas uma identidade já validada.

---

## Impacto no Domínio

Nenhum acoplamento com FastAPI ou JWT será introduzido.

A entidade `Device` continuará pura.

---

## Impacto na Aplicação

Casos de uso protegidos poderão passar a receber o identificador do Device autenticado para validar propriedade e autorização.

---

## Impacto na API

Rotas protegidas passarão a exigir:

```http
Authorization: Bearer <access_token>
```

Chamadas sem credenciais deixarão de funcionar.

Essa mudança será versionada e documentada antes da integração com o Nebula Player.

## Critérios de Aceite

A ADR será considerada implementada quando:

- endpoints protegidos exigirem Bearer Token;
- tokens inválidos retornarem `401`;
- respostas `401` incluírem `WWW-Authenticate: Bearer`;
- Devices não ativos retornarem `403`;
- o Device autenticado vier do banco;
- nenhuma rota decodificar JWT diretamente;
- Sessions não puderem ser manipuladas por outro Device;
- Swagger apresentar o esquema Bearer;
- todos os testes permanecerem verdes.
