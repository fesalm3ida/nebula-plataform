# ADR-026 — Nebula Admin Service (Backend for Frontend)

- **Status:** Accepted
- **Data:** 2026-09-06
- **Versão:** Nebula Platform v1.0
- **Autores:** Nebula Team

---

# Contexto

A plataforma precisa de uma interface administrativa (Nebula Admin) para gestão
de dispositivos, playlists e dados operacionais. O Nebula Core é o único
proprietário do domínio e da persistência (PostgreSQL). A regra de fronteira do
ecossistema é que **só o Core acessa o banco**; os demais módulos consomem via
API.

---

# Decisão

Criar um serviço independente — **Nebula Admin** — como **Backend for Frontend
(BFF)**, em **FastAPI**, responsável pela identidade administrativa, autorização
(RBAC), composição/agregação de respostas do Core e pela adaptação dos contratos
do Core às necessidades da UI administrativa.

```
Flutter Admin (UI)
   │  HTTPS + Admin JWT
   ▼
Nebula Admin (FastAPI / BFF)
   │  HTTPS + service credential (X-Admin-Token)
   ▼
Nebula Core (FastAPI)  ← único dono do banco
   │
   ▼
PostgreSQL
```

## Princípios

- **Nebula Admin não acessa diretamente o PostgreSQL.**
- **Nebula Admin não cria models SQLAlchemy das entidades do Core** (não possui
  migrations das tabelas do Core, não duplica regras de domínio).
- O Admin consome as funcionalidades do Core **exclusivamente por API**, por meio
  de um `NebulaCoreGateway` (porta) centralizado em
  `infrastructure/clients/httpx_nebula_core_client.py`.
- **Fluxos oficiais:** `Player → Core`, `Admin UI → Admin Service → Core`,
  `Core → PostgreSQL`.
- **Não introduzir** Kubernetes/Kafka/service mesh/message broker (YAGNI).
  Operação leve e modular (ex.: Docker Compose com nginx, nebula-admin,
  nebula-core, postgres).

## Autenticação (identidades separadas)

- **Player/Device → Core:** DeviceKey, Access Token, Session (mecanismos do Core).
- **Admin (humano) → Flutter Admin → Nebula Admin:** credenciais administrativas
  próprias → **Admin JWT**. Não reutilizar a identidade de Device.
- **Admin → Core:** credencial de serviço (service-to-service). O Core não
  depende de detalhes da interface administrativa.

---

# Consequências

## Benefícios

- Separação clara de responsabilidades (domínio/persistência no Core;
  identidade administrativa e BFF no Admin).
- A UI consome contratos adaptados (composição/agregação p/ tela).
- Possibilidade de RBAC e auditoria administrativa sem tocar o Core.
- Consistência tecnológica (FastAPI/Pydantic) entre os serviços.

## Trade-offs

- Um serviço a mais para operar.
- Latência/indireção adicional (Admin → Core).
- O Core precisa expor endpoint administrativo para cada operação que o Admin
  consuma (ex.: ainda não há `GET /devices` para listagem — evolução futura).

# Estrutura

```text
backend/nebula-admin/
├── app/
│   ├── main.py
│   ├── core/config.py
│   ├── domain/            # entidade Admin (identidade própria)
│   ├── application/       # ports (NebulaCoreGateway), use cases, AdminTokenService
│   ├── infrastructure/    # admin_store, clientes (HTTPX), JWTAdminTokenService
│   └── api/               # rotas, schemas, dependencies, security (current_admin)
└── tests/
```

**Accepted**

administrativa separada e comunicação service-to-service com o Core.
