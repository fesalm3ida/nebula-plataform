# ADR-023 — Schema de Payload de TelemetryEvent

- **Status:** Accepted
- **Data:** 2026-09-06
- **Versão:** Nebula Core v0.4.x
- **Autores:** Nebula Team

---

# Contexto

O subdomínio de observabilidade (ADR-022) define `TelemetryEvent` como o evento
de comportamento e experiência. Para que o Nebula Monitor e os dashboards
consumam a telemetria de forma consistente, o payload precisa de um **esquema
padrão** (AB-009).

---

# Decisão

Padronizar o `TelemetryEvent` com os seguintes campos:

```
TelemetryEvent
├── event_id (UUID)
├── session_id (UUID)
├── device_id (UUID)
├── event_type (enum) — catálogo tipado
├── occurred_at (timestamp com timezone)
├── received_at (timestamp com timezone)
└── payload (JSON) — estrutura do evento
```

- `event_id`: identificador único do evento.
- `session_id` / `device_id`: contexto do evento.
- `event_type`: catálogo tipado de eventos (ex.: `playback_started`,
  `buffer_underrun`, `channel_changed`, `qos_report`).
- `occurred_at`: quando o evento ocorreu no dispositivo (obrigatório, com timezone).
- `received_at`: quando o Core recebeu o evento.
- `payload`: dados específicos do tipo de evento.

O catálogo de `event_type` é versionado e o `payload` é uma estrutura tipada por
tipo de evento, permitindo evolução sem quebrar consumidores.

---

# Consequências

## Benefícios

- Ingestão e consulta padronizadas.
- Interoperabilidade com o Nebula Monitor.
- Catálogo tipado facilita validação e agregação.
- Versionamento permite evolução.

## Trade-offs

- Exige contrato e versionamento exigentes.
- O `payload` JSON precisa de validação por tipo de evento.
