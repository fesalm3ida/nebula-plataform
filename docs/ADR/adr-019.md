# ADR-019 — Autenticação de Devices com JSON Web Token

- **Status:** Aceita
- **Data:** 2026-07-15
- **Autor:** Nebula Software House
- **Decisores:** Equipe Nebula
- **Versão:** First Light
- **Relacionadas:** ADR-001, ADR-016, ADR-017, ADR-018
- **Impacto:** Core / Segurança / Player / API

---

## Contexto

O Nebula Core já possui um fluxo funcional de autenticação de Devices.

Atualmente, após validar:

- `device_id`;
- `device_key`;
- `fingerprint`;
- status ativo do Device;

o caso de uso `AuthenticateDeviceUseCase` gera um token aleatório com:

```python
token_urlsafe(32)
```

Esse token não possui estrutura verificável, claims, emissor, audiência ou assinatura padronizada.

Com a evolução da plataforma, o token precisará ser consumido por:

- Nebula Player;
- Nebula Core;
- Nebula Admin;
- Nebula Monitor;
- serviços futuros do ecossistema.

Torna-se necessário adotar um formato padronizado, verificável e interoperável.

JWT é um formato compacto e seguro para URL, destinado à representação de claims entre partes. O padrão define claims registradas como `iss`, `sub`, `aud`, `exp`, `nbf`, `iat` e `jti`. :contentReference[oaicite:0]{index=0}

---

## Problema

Como emitir tokens de acesso verificáveis para Devices autenticados sem acoplar o domínio a uma biblioteca específica de JWT?

---

## Decisão

O Nebula Core utilizará JSON Web Token para emitir access tokens de Devices autenticados.

O token será criado somente após a validação completa das credenciais do Device.

A emissão e a validação dos tokens pertencerão à camada de aplicação e infraestrutura de segurança.

O domínio não conhecerá:

- JWT;
- algoritmos de assinatura;
- chaves criptográficas;
- headers HTTP;
- bibliotecas de token;
- detalhes de transporte.

---

## Tipo de Token

Nesta primeira implementação será criado:

```text
Access Token
```

O access token terá curta duração e será usado para autorizar requisições do Nebula Player ao Core.

Refresh Tokens não serão implementados nesta etapa.

Eles serão tratados em uma ADR posterior, pois exigem decisões adicionais sobre:

- rotação;
- revogação;
- persistência;
- reutilização;
- comprometimento de credenciais.

---

## Claims Obrigatórias

O access token deverá conter, no mínimo:

```text
iss
sub
aud
iat
nbf
exp
jti
device_id
token_type
```

### `iss`

Identifica o emissor:

```text
nebula-core
```

### `sub`

Identifica o principal autenticado.

Para tokens de Device:

```text
device:{device_id}
```

### `aud`

Identifica o destinatário esperado:

```text
nebula-player
```

### `iat`

Instante de emissão.

### `nbf`

Instante a partir do qual o token pode ser aceito.

### `exp`

Instante de expiração.

### `jti`

Identificador único do token.

### `device_id`

Claim privada contendo o UUID do Device autenticado.

### `token_type`

Tipo lógico do token:

```text
access
```

---

## Exemplo de Payload

```json
{
  "iss": "nebula-core",
  "sub": "device:73aa9ac9-66c2-4d2a-b748-75ad7da23aba",
  "aud": "nebula-player",
  "iat": 1784160000,
  "nbf": 1784160000,
  "exp": 1784161800,
  "jti": "d46874b5-868e-42e4-8a84-4a4c88870693",
  "device_id": "73aa9ac9-66c2-4d2a-b748-75ad7da23aba",
  "token_type": "access"
}
```

## Assinatura

A primeira implementação utilizará assinatura simétrica:

```text
HS256
```

A chave será mantida fora do código-fonte e fora dos arquivos versionados.

Ela será carregada por secret local durante desenvolvimento e, futuramente, por um gerenciador de segredos em produção.

A aplicação nunca aceitará o algoritmo informado livremente pelo token como fonte de verdade.

O algoritmo permitido será configurado explicitamente pelo servidor durante a validação.

A biblioteca deverá validar a assinatura e as claims temporais ao decodificar o token. A documentação do PyJWT demonstra a codificação e a validação de tokens assinados, incluindo verificação de expiração e algoritmo permitido. :contentReference[oaicite:1]{index=1}

---

## Duração

O access token terá duração inicial de:

```text
30 minutos
```

O valor será configurável por ambiente.

Exemplo:

```dotenv
JWT_ACCESS_TOKEN_EXPIRE_MINUTES=30
```

---

## Armazenamento da Chave

Durante o desenvolvimento:

```text
backend/nebula-core/.secrets/jwt_secret_key
```

O arquivo não poderá ser versionado.

Permissões esperadas:

```text
600
```

Em produção, a chave deverá vir de um serviço de gerenciamento de segredos.

---

## Fluxo Arquitetural

```text
Nebula Player
      │
      │ device_id + device_key + fingerprint
      ▼
POST /auth/device
      │
      ▼
AuthenticateDeviceUseCase
      │
      ├── valida Device
      ├── valida credenciais
      └── valida status
      │
      ▼
AccessTokenService
      │
      ▼
JWT assinado
      │
      ▼
Nebula Player
```

Nas requisições autenticadas:

```text
Authorization: Bearer <token>
```

O FastAPI oferece integração com o padrão Bearer e fluxos de autenticação baseados em JWT por meio de dependências de segurança. :contentReference[oaicite:2]{index=2}

## Responsabilidades

### Domínio

Responsável por:

- identidade do Device;
- status do Device;
- invariantes;
- credenciais de domínio.

Não conhece tokens.

### Aplicação

Responsável por:

- orquestrar a autenticação;
- solicitar a criação do access token;
- retornar o resultado da autenticação.

### Infraestrutura de Segurança

Responsável por:

- assinar JWT;
- validar JWT;
- converter claims;
- verificar emissor;
- verificar audiência;
- verificar expiração;
- verificar algoritmo;
- carregar chaves.

### API

Responsável por:

- receber credenciais;
- devolver o token;
- extrair Bearer Token;
- traduzir falhas de autenticação em respostas HTTP.

---

## Contrato de Aplicação

Será criado um contrato abstrato:

```python
class AccessTokenService(ABC):
    @abstractmethod
    def create_device_access_token(
        self,
        device_id: UUID,
    ) -> AccessToken:
        ...
```

O caso de uso dependerá do contrato, não diretamente do PyJWT.

A implementação concreta ficará na infraestrutura:

```text
JWTAccessTokenService
```

---

## Resultado de Autenticação

O resultado deverá continuar expondo:

```text
access_token
expires_at
device_status
```

E passará a expor também:

```text
token_type
```

Valor:

```text
bearer
```

---

## Validação

A validação deverá rejeitar tokens com:

- assinatura inválida;
- algoritmo diferente do permitido;
- emissor incorreto;
- audiência incorreta;
- expiração vencida;
- `nbf` ainda não atingido;
- `token_type` diferente de `access`;
- `device_id` ausente ou inválido;
- subject inconsistente.

---

## Revogação

JWTs de curta duração não terão revogação individual nesta primeira implementação.

O bloqueio, revogação ou expiração do Device continuará sendo verificado em operações sensíveis que carreguem o Device do banco.

A futura implementação de Refresh Token poderá introduzir:

- rotação;
- blacklist;
- token families;
- revogação centralizada;
- detecção de reutilização.

---

## Benefícios

- token padronizado;
- assinatura verificável;
- claims estruturadas;
- expiração explícita;
- interoperabilidade entre serviços;
- suporte a autorização futura;
- compatibilidade com Bearer Authentication;
- separação entre aplicação e biblioteca JWT.

---

## Trade-offs

- gestão segura de chave;
- necessidade de validação rigorosa de claims;
- impossibilidade inicial de revogação imediata de cada access token;
- aumento da complexidade de segurança;
- necessidade de rotação futura de chaves.

---

## Alternativas Consideradas

### Token aleatório opaco

Rejeitado como solução definitiva.

Não carrega claims e exige persistência ou consulta central para validação.

### JWT assimétrico desde o início

Adiado.

Algoritmos como RS256 ou EdDSA facilitam validação distribuída, mas introduzem gestão de pares de chaves e rotação mais complexa.

A adoção futura permanece possível sem alterar o domínio.

### Sessão autenticada armazenada apenas no banco

Rejeitada como mecanismo principal de autenticação HTTP.

Aumentaria consultas para cada requisição e não forneceria um formato interoperável entre serviços.

---

## Impacto no Domínio

Nenhum.

As entidades `Device` e `Session` continuarão sem dependências de autenticação JWT.

---

## Impacto na API

O endpoint existente continuará sendo:

```http
POST /auth/device
```

Resposta planejada:

```json
{
  "access_token": "<jwt>",
  "token_type": "bearer",
  "expires_at": "2026-07-15T23:30:00Z",
  "device_status": "active"
}
```

Endpoints protegidos passarão gradualmente a exigir:

```http
Authorization: Bearer <jwt>
```

---

## Impacto na Configuração

Serão adicionadas configurações equivalentes a:

```dotenv
JWT_ISSUER=nebula-core
JWT_AUDIENCE=nebula-player
JWT_ALGORITHM=HS256
JWT_ACCESS_TOKEN_EXPIRE_MINUTES=30
```

A chave será lida de:

```text
.secrets/jwt_secret_key
```

## Critérios de Aceite

A ADR será considerada implementada quando:

- o Core emitir JWT assinado;
- a chave não estiver no Git;
- o token contiver todas as claims obrigatórias;
- tokens expirados forem rejeitados;
- tokens com assinatura inválida forem rejeitados;
- emissor e audiência forem verificados;
- o algoritmo permitido for fixado pelo servidor;
- o caso de uso não importar PyJWT;
- todos os testes permanecerem verdes;
- a documentação OpenAPI apresentar autenticação Bearer.
