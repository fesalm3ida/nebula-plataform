# ADR-022 — Subdomínio de Observabilidade

- **Status:** Accepted
- **Data:** 2026-09-06
- **Versão:** Nebula Core v0.4.x
- **Autores:** Nebula Team

---

# Contexto

A Nebula Platform acumula um conjunto crescente de informações sobre o
comportamento operacional dos dispositivos:

- Heartbeats;
- TelemetryEvents;
- Logs;
- métricas de reprodução;
- métricas de QoS;
- alertas;
- disponibilidade.

Esses dados **não são regras de negócio**: são eventos gerados durante a
utilização da plataforma. Tratá-los como entidades transacionais acopla o
domínio de negócio (Device, Session, Playlist) a conceitos operacionais e
dificulta a evolução do volume de eventos (RFC-003 e RFC-005).

---

# Decisão

Criar um **Subdomínio de Observabilidade** dentro do Nebula Core, com modelos
próprios, separado do domínio transacional.

As entidades de observabilidade respeitam o princípio da Responsabilidade
Única, todas vinculadas a uma `Session` como contexto temporal:

```
Session (contexto temporal)
   ├── Heartbeat       → saúde e conectividade
   ├── TelemetryEvent  → comportamento e experiência
   └── Log             → diagnóstico técnico
```

- **Session:** contexto temporal.
- **Heartbeat:** saúde e conectividade (presença).
- **TelemetryEvent:** comportamento e experiência do usuário.
- **Log:** diagnóstico técnico.

O domínio transacional permanece focado em regras de negócio e não depende
das entidades de observabilidade.

---

# Modelo Conceitual

```
ObservabilitySubdomain
   ├── Heartbeat { session_id, occurred_at }
   ├── TelemetryEvent { session_id, event_type, payload, occurred_at }
   └── Log { session_id, level, message, occurred_at }
```

---

# Consequências

## Benefícios

- Separação clara entre negócio e observação (SRP).
- O domínio transacional não acopla a eventos.
- Permite estratégia própria de armazenamento e retenção.
- Base para o Nebula Monitor consumir uma fonte única de eventos.
- Compatível com Clean Architecture.

## Trade-offs

- Mais modelos e contratos a manter.
- Exige pipeline de ingestão e agregação dedicados.
- Retenção/volume precisam de política própria (ver ADR-024).

---

# Alternativas Consideradas

## Manter no domínio operacional

Rejeitada. Acoplaria regras de negócio a eventos e dificultaria o crescimento
do volume de telemetria.

## Microserviço de observabilidade

Adiada. O volume atual não justifica a separação física; o subdomínio dentro
do Core mantém a simplicidade e permite evoluir para um serviço depois.
