# ADR-015 — Interfaces de Repositório pertencem ao Domínio

- **Status:** Aceita
- **Data:** 2026-07-11
- **Decisores:** Equipe de Arquitetura Nebula

---

# Contexto

O Nebula Core adota os princípios de Domain-Driven Design (DDD) e Clean Architecture, buscando manter o domínio independente de detalhes de infraestrutura.

As entidades e casos de uso do domínio necessitam persistir e recuperar informações, porém não devem conhecer tecnologias específicas como PostgreSQL, SQLite, Redis, MongoDB ou qualquer outro mecanismo de armazenamento.

Sem uma abstração adequada, o domínio ficaria acoplado diretamente às implementações de persistência, reduzindo a flexibilidade da arquitetura e dificultando testes automatizados.

---

# Problema

Como permitir que o domínio persista e consulte dados sem depender de uma tecnologia específica de banco de dados?

---

# Decisão

As interfaces (contratos) de repositório pertencem à camada de **Domínio**.

As implementações concretas desses contratos pertencem à camada de **Infraestrutura**.

Exemplo:

```text
Domain
│
├── Entities
├── Value Objects
├── Enums
└── Repositories
      └── DeviceRepository
              ▲
              │
Infrastructure
│
├── InMemoryDeviceRepository
├── PostgreSQLDeviceRepository
├── SQLiteDeviceRepository
└── MockDeviceRepository
```

Os Casos de Uso dependem exclusivamente das interfaces definidas no domínio.

Em nenhum momento o domínio poderá depender de bibliotecas como:

- SQLAlchemy
- Psycopg
- Redis Client
- MongoDB Driver
- ORM específico

---

# Justificativa

Essa decisão segue o Princípio da Inversão de Dependência (Dependency Inversion Principle - SOLID), onde módulos de alto nível não dependem de módulos de baixo nível.

O domínio representa as regras de negócio da plataforma Nebula e deve permanecer independente de qualquer decisão tecnológica.

Dessa forma:

- o domínio permanece testável;
- a infraestrutura pode evoluir sem impactar as regras de negócio;
- múltiplas implementações podem coexistir;
- o banco de dados pode ser substituído sem alterar o domínio.

---

# Consequências

## Positivas

- Baixo acoplamento entre domínio e infraestrutura.
- Facilidade para testes unitários utilizando repositórios em memória.
- Facilidade para substituir tecnologias de persistência.
- Maior aderência aos princípios da Clean Architecture.
- Maior longevidade da arquitetura.

## Negativas

- Maior número de classes e interfaces.
- Necessidade de implementar adaptadores para cada tecnologia de persistência.
- Pequeno aumento da complexidade inicial do projeto.

---

# Notas de Implementação

As interfaces deverão ser armazenadas em:

```text
backend/
└── nebula-core/
    └── app/
        └── domain/
            └── repositories/
```

As implementações deverão ser armazenadas em:

```text
backend/
└── nebula-core/
    └── app/
        └── infrastructure/
            └── repositories/
```

Exemplo:

```text
domain/
└── repositories/
      device_repository.py

infrastructure/
└── repositories/
      in_memory_device_repository.py
      postgresql_device_repository.py
```

Os Casos de Uso receberão as interfaces por injeção de dependência, sem conhecer a implementação concreta.

---

# Considerações Futuras

Inicialmente, o Nebula Core utilizará uma implementação em memória (`InMemoryDeviceRepository`) para acelerar o desenvolvimento do MVP.

Em fases posteriores, será adicionada uma implementação baseada em PostgreSQL utilizando SQLAlchemy, sem necessidade de alterações nas entidades ou nos Casos de Uso.

Outras implementações poderão ser adicionadas conforme a evolução da plataforma.
