# ADR-006

## Título

Separação entre ContentProvider e ProviderAccount

---

## Status

**Aceito**

---

# Contexto

Durante a modelagem do domínio da Nebula Platform identificou-se que uma conta utilizada para obtenção de conteúdo não representa o provedor em si.

A plataforma deverá permitir a integração com diferentes provedores de conteúdo, atuais ou futuros, sem alterar sua arquitetura.

Atualmente os endpoints M3U são gerados manualmente por uma plataforma externa, porém essa implementação não deve influenciar o domínio da Nebula.

---

# Problema

Modelar apenas uma entidade denominada **ProviderAccount** faria com que a plataforma assumisse implicitamente que existe apenas um provedor de conteúdo.

Essa abordagem dificultaria futuras integrações com:

- outros provedores IPTV;
- APIs próprias;
- provedores de VOD;
- provedores de Streaming;
- infraestrutura própria da Nebula.

---

# Decisão

O domínio será dividido em duas entidades distintas.

## ContentProvider

Representa o fornecedor de conteúdo.

Exemplos:

- IPTV Provider A
- IPTV Provider B
- IPTV Provider C
- Nebula Internal Provider

Cada ContentProvider poderá possuir uma ou mais contas.

---

## ProviderAccount

Representa uma conta cadastrada em um determinado ContentProvider.

Cada ProviderAccount poderá possuir um ou mais Servidores.

---

# Modelo Conceitual

```text
ContentProvider
        │
        │ 1
        ▼
ProviderAccount
        │
        │ 1:N
        ▼
Server
        │
        │ 1:N
        ▼
ContentEndpoint
        │
        ▼
Nebula Core
        │
        ▼
Device
```

---

# Responsabilidades

## ContentProvider

Responsável por representar o fornecedor de conteúdo.

Não possui informações operacionais relacionadas ao acesso.

---

## ProviderAccount

Responsável por armazenar as credenciais necessárias para acesso ao fornecedor.

Cada conta poderá possuir múltiplos servidores.

---

## Server

Representa um servidor de conteúdo pertencente a uma ProviderAccount.

---

## ContentEndpoint

Representa um endpoint autorizado de conteúdo disponibilizado por um Server.

No MVP será utilizado exclusivamente o tipo **M3U**.

A arquitetura deverá permitir futuramente outros tipos de endpoint.

---

# Regras

- Um ContentProvider pode possuir várias ProviderAccounts.
- Uma ProviderAccount pertence a apenas um ContentProvider.
- Uma ProviderAccount pode possuir vários Servers.
- Um Server pertence a apenas uma ProviderAccount.
- Um Server pode disponibilizar um ou mais ContentEndpoints.
- Um ContentEndpoint pertence a apenas um Server.
- Apenas o Nebula Core poderá disponibilizar ContentEndpoints aos Devices.

---

# Benefícios

- Separação clara entre fornecedor e conta.
- Arquitetura preparada para múltiplos provedores.
- Independência da plataforma atualmente utilizada.
- Facilidade para migração futura.
- Maior escalabilidade do domínio.
- Redução do acoplamento.

---

# Consequências

O domínio passa a possuir uma hierarquia de distribuição de conteúdo.

ContentProvider

↓

ProviderAccount

↓

Server

↓

ContentEndpoint

↓

Device

Essa estrutura permitirá que novos provedores sejam adicionados sem alterações estruturais no restante da plataforma.

---

# Observações

No MVP todos os ContentEndpoints serão do tipo **M3U**.

Entretanto, a entidade ContentEndpoint deverá ser modelada de forma genérica para permitir futuramente:

- Xtream Codes
- APIs REST
- DASH
- HLS
- Outros formatos de distribuição de conteúdo
